[Galgame 怎麼接進 Fushi？](/faq/galgame.zh-HK)講的是怎麼用；這篇回答更底層的幾個問題：Fushi 是怎麼把臺詞從遊戲裡拿出來的、為什麼只能在 Windows 上、到底支援哪些引擎、支援到什麼程度，以及「在遊戲畫面裡直接點字查詞」是怎麼做到的。

先說結論：**文本 Hook 只在 Windows 上做**，而且「支援」分好幾個等級——下面的引擎列表照抄 Fushi 倉庫裡的引擎支援清單（`native/galgame_hook/engine-support.yaml`），沒在真實遊戲上驗證過的，一律寫「未驗證」。

## 原理：注入 helper + LunaHook + 引擎適配

當你點 **啟動並捕獲**（或對已執行的遊戲點 **附著並捕獲**）時，Fushi 做的事情大致是：

1. **拉起一個隔離的注入器**：注入用的元件是單獨構建的 x86 / x64 兩套 helper（注入器 exe + Hook DLL），**不連結進 Fushi 主程式**，主程式只把注入器當子程序啟動。兩套 helper 在構建時就隨 Windows 安裝包一起放程序序目錄，執行時不會再去網上下載任何元件。32 位遊戲用 x86 那套，64 位遊戲用 x64 那套，Fushi 按遊戲自動選。
2. **把 Hook 注入遊戲程序**：helper 裡帶著開源的 LunaHook（取自 [LunaTranslator](https://github.com/HIllya51/LunaTranslator) 的釋出版，和 Fushi 一樣是 GPLv3），負責通用的文本抓取——它認識大量引擎的文本函式，抓到的文字按「文本執行緒」分開，所以第一次要在會話面板裡選那條幹淨的臺詞執行緒。
3. **按引擎適配補齊其他能力**：LunaHook 只管文字。逐句語音、遊戲內查詞要靠 Fushi 針對每個引擎寫的適配：從遊戲的語音資源包或解碼器裡拿到**這一句**的原始語音，或者在引擎的音訊輸出（XAudio2 / DirectSound）處擷取 PCM；都拿不到時才退回錄製系統混音（Loopback，會混進 BGM 和音效）。
4. **通過共享記憶體回傳**：helper 把臺詞、語音、狀態寫進共享記憶體，Fushi 主程式讀出來配對成「這句臺詞 + 這句語音 + 這一刻的截圖」，在臺詞浮窗裡給你點字查詞、一鍵制卡。

引擎識別靠的是**引擎自己的結構特徵**（匯出函式、外掛介面、執行時模組、資源包格式等），而不是遊戲的檔名或標題。所以同一個引擎的其他遊戲通常能一起受益；反過來，同引擎的新版本或加殼版改了結構，也可能需要單獨適配。

## 為什麼只支援 Windows？

Galgame 絕大多數是 Windows 程式，文本 Hook 的本質是把程式碼注入遊戲程序、攔截它的函式呼叫——這隻能在遊戲執行的那臺 Windows 電腦上做。Fushi 的 Hook、helper、引擎適配都只做 Windows（x86 / x64），Android、iOS、macOS、Linux 上沒有文本 Hook，也不宣稱支援。

想在手機或 iPad 上玩：遊戲和 Hook 留在 Windows 電腦上，用**遊戲串流**把畫面、聲音和臺詞推到手機上查詞制卡，見[能不能在手機 / iPad 上玩電腦裡的 Galgame？](/faq/game-streaming.zh-HK)。

## 支援哪些引擎？按清單的實際狀態

清單對每個引擎分四個等級：

- **已驗證**：在真實遊戲的原始啟動路徑上驗證過列出的能力，只覆蓋記錄在案的版本和能力；
- **部分驗證**：至少一條採集路徑真機驗證過，但還有關鍵能力受限或未驗證；
- **已實現、未驗證**：程式碼已經有了，但沒有足夠的真實遊戲證據，**不能算支援**；
- **不可用**：當前沒有實現。

**已驗證**（清單裡的「verified」）：

- **SiglusEngine**：在 anemoi 正式版（x86）上驗證了逐句語音（koe 目錄 OVK 語音包裡的原始 Ogg，與原始檔逐位元組一致）和 DirectSound 採集；文本抓取與遊戲內查詞這兩項本身仍標為未驗證。
- **Unity IL2CPP**：在 manosaba（x64）上驗證了 LunaHook 通用文本、TextMeshPro 文本事件和 AudioClip 語音資源配對。Unity Mono 是另一條，見下面。
- **XAudio2 / DirectSound 通用採集**：不是一個引擎，而是通用的音訊擷取層，在 KiriKiriZ 和 Siglus 樣本上採到過非靜音 PCM。注意它截到的可能是軟體混音後的整路聲音，不一定是乾淨人聲。

**部分驗證**（「partial」）：

- **KiriKiri2 / KiriKiri Z**：通用採集到了 PCM，但驗證樣本把語音、BGM、音效混在一路輸出裡；資源包與解碼器的 Hook 在官方體驗版上裝上了，但還沒走過一句有配音的臺詞，**不宣稱乾淨的逐句語音**。
- **TyranoScript / NW.js**：在免費全語音作品「かえりみち」（x64）上，匯出的逐句語音與遊戲資源逐位元組一致；只認 `data/sound/v_*` 約定的 OGG / M4A，自定義語音目錄或加密包不在內。
- **Artemis Engine（PF8）**：在「アマナツ 體験版」（x64）上驗證了 PF8 包裡 `sound/vo` 的 Ogg 語音；PF6 解析已實現但沒有真實樣本跑過。
- **CatSystem2（KIF / INT）**：在官方「CatSystem2 入門セット」用本地生成的語音驗證了未加密 `pcm_*.int` 裡的 Ogg；帶 `__key__.dat` 的加密商業包會被主動拒絕，不對商業作品做語音宣告。
- **QLIE（FilePack）**：在「美少女萬華鏡 -理と迷宮の少女- 體験版」（x86）上驗證了按聲源分開的解碼後 PCM；只覆蓋測過的那個版本。

**已實現、未驗證**（「implemented_unverified」，程式碼在、證據不夠，不算支援）：elf AI6、RealLive / 舊 VisualArt's、CMVS（Purple Software）、Ren'Py / FFmpeg、BGI / Ethornell、Malie System（LIBP）、Leaf / AQUAPLUS（只有 WHITE ALBUM2 一個精確配置，不代表整個廠牌）、HUNEX GGE、smash / fzmedia（TYPE-MOON）、M2 wind3d11（STEINS;GATE RE:BOOT）、Unreal Engine（IoStore）、AOS / SFA、Unity（Mono）、YU-RIS、FVP、工畫堂 Hy 引擎、LucaSystem。

**不在清單裡的引擎**：LunaHook 的通用文本抓取照樣會嘗試，很多遊戲也能出字，只是沒有專門的語音和查詞適配，語音會退回通用採集或系統混音。抓不到字時可以試 **特殊碼**（H-code），用法見[Galgame 怎麼接進 Fushi？](/faq/galgame.zh-HK)。

## 查詞卡怎麼在遊戲畫面裡彈出來？

除了臺詞浮窗，Fushi 還在做 **遊戲內查詞**：不看浮窗，直接點遊戲畫面裡的字，查詞卡就彈在遊戲畫面上。難點有兩個：

1. **知道每個字在螢幕上的位置**（幾何）。來源有三種：引擎執行時的排版資訊、引擎內部精確的文字佈局，以及**手動校準**——在會話面板的「遊戲內查詞」裡點 **校準**，按提示在遊戲裡依次點第一個、中間、最後一個字，Fushi 記下正文框和字格。遊戲內查詞**不使用 OCR**，目前只支援橫排正文。模式有「自動 / 僅校準層 / 僅原生幾何 / 關閉」。
2. **點字查詞時不能推進遊戲**。點遊戲畫面本來就是「下一句」，Fushi 的「輸入盾」要在查詞那一下把點選攔下來；攔不全的遊戲，裸左擊可能同時推進臺詞或觸發選項，面板上會標出點選風險。

查詞卡本身是 Fushi 渲染的：有的引擎（如 KiriKiri）由 Hook 把卡片畫進遊戲自己的圖層，其他情況是蓋在遊戲視窗上、不搶遊戲前臺的 Fushi 視窗。觸屏點按、長按、滑動也要同樣不推進遊戲、不搶前臺，這是適配驗收的必測項。

**如實說明現狀**：清單裡所有引擎的遊戲內查詞（幾何、輸入盾、點選風險）目前都還是「已實現、未驗證」。也就是說它可以試，但沒有哪個引擎能保證點字一定不推進劇情。穩妥的做法仍是臺詞浮窗查詞，或者先存檔再試。

## 「適配成功」怎麼算？

Fushi 對一款遊戲「適配成功」有明確標準，在使用者真實的啟動路徑上**四條同時滿足**才算，缺一條只算部分適配：

1. **文本**：能 Hook 到當前臺詞正文，選定的執行緒是乾淨正文；
2. **音訊**：能拿到和這一句對應的語音（引擎資源或引擎 PCM，純系統混音不算）；
3. **遊戲內查詞**：遊戲畫面內能彈出 Fushi 查詞卡；
4. **點選查詞不推進**：用滑鼠和 Windows 觸屏點字查詞，都不會推進遊戲進度。

適配也只做**引擎級**：某款遊戲出問題，修的是它所屬引擎的通用判據，不為單個遊戲寫死特判。所以你的遊戲不工作時，最有用的資訊是**引擎名、遊戲版本、32/64 位、從哪裡啟動**，通過[應用內反饋](/faq/feedback.zh-HK)發過來。
